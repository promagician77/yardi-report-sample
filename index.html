The second way custom reports go wrong is slower. They work for a year, Yardi pushes a Voyager upgrade, and on Monday morning the client’s report is throwing an error or — worse — returning numbers that are quietly off. Most of it is avoidable at write time.

Prefix every custom object

Procedures, views and functions go out as cu_ so an upgrade recognises them as yours and leaves them alone. An unprefixed object sitting in dbo is a candidate for replacement.

Read documented columns, not convenient ones

Voyager carries columns that are internal and columns that are contractual. Building on the first kind is what breaks on upgrade. Where Yardi publishes a view for something, the view is the safer surface even when the base table is faster to write against.

Assume SaaS until told otherwise

On Yardi Cloud you generally cannot create your own database objects; custom SQL goes through Yardi to be deployed, and that queue has a lead time. It changes how a project is sequenced, so it is worth establishing per client on day one rather than discovering it at delivery.

Never hardcode a client’s chart of accounts

GL codes, charge codes and property codes differ at every client you serve. They belong in parameters or lookup joins, so the same report can be lifted to the next client with a parameter change instead of a rewrite.

Ship a regression check with the report

A short script that runs the report against known inputs and compares the totals. Run it after an upgrade and you know in minutes whether anything moved, rather than waiting for the client to find it.

Write the handover for your consultant, not for me

Parameters, source tables, assumptions, and what the report deliberately excludes. Your team fields the client’s questions, so the documentation has to answer them without me in the room.

Why I built this rather than listing reports I’ve written

Your posting is short and the work is project-by-project, so the thing worth proving is not that I can name Voyager tables. It is what I do before a report reaches your client — because when it goes wrong, the call comes to your firm with your name on it, not mine.

How I’d work with a consulting firm

  • Scoped per report. A short spec first: parameters, grouping, totals, what is deliberately excluded. Signed off before I write SQL, so there is no second round over what “outstanding” meant.
  • Your name on the delivery. Documentation written for your consultants to hand straight to the client. No branding of mine anywhere in it.
  • Improving inherited reports too. Half this work is someone else’s undocumented RDL. I read it, write down what it actually does, confirm that against what the client thinks it does, and fix the gap — that gap is usually the real bug.
  • Quiet by default. Project-by-project means you should not have to manage me. Spec, build, test against real data, deliver, answer questions.

What I’d need at the start of each project

  • Whether that client is on Yardi Cloud or self-hosted, and who deploys.
  • Voyager version and platform, plus SSRS or YSI Reporting for this one.
  • A test database or a sanitised copy, and a user whose results we can both check.
  • For a rebuild: the existing RDL and whatever the client has said is wrong with it.

About this sample

The database behind these figures is synthetic: eight properties, 442 units, 417 tenants, built to Voyager’s conventions — hMy primary keys, h-prefixed foreign keys, AR activity in artran, and a per-user property list standing in for Voyager’s security lists. The figures on the first tab are real query results against it, not illustrations. The stored procedure is written in T-SQL for Voyager; the demo numbers were produced by running the identical logic against the sample database.

Happy to walk through any of it, or take a real report of yours and say what I’d change before it goes out.
